# V1 收官范围

## 项目定位

这是一个面向客服场景的可运行项目，不是单纯的聊天机器人。

V1 的目标是完成一个可观测、可评测、可演示的项目，重点展示以下能力：

- 基于 RAG 和 Tool Calling 提升回答准确性
- 基于 Plan-Execute 和 ReAct 展示任务分解与执行
- 基于 Multi-Agent 展示职责拆分与协作思路
- 基于 SSE 和调试面板展示工程化交互能力

一句话定义：

> 一个可观测、可评测、可演示的客服项目

## V1 要解决的问题

V1 仅聚焦在一个明确问题域：

- 用户咨询订单、退款、登录、发票、地址修改等客服问题时，系统能够识别意图，检索知识，必要时调用工具，并输出可信、可解释的回答。

## V1 必须包含的能力

### 1. 基础 Agent 主链路

必须具备完整处理流程：

- 用户输入
- 意图 / 情绪 / 紧急度分析
- 知识检索
- 计划生成
- 工具调用
- 最终回答
- 前端流式展示

### 2. 真实模型接入

- 支持真实模型，而不是只停留在 dummy 模式
- 能切换到 DashScope / Qwen 等真实模型提供商

### 3. RAG 最小闭环

- 文档导入
- 向量检索
- 检索结果参与回答
- 回答尽量 grounded，避免直接编造

### 4. Tool Calling 最小闭环

- 至少 2 个可用工具
- 工具有清晰 schema
- 工具输出会进入最终回答
- 工具结果优先于模型猜测

### 5. Plan-Execute / ReAct 展示能力

- 前端或日志里能看到 plan / action / observation
- 能讲清楚 planner 和 executor 的区别

### 6. Multi-Agent 职责拆分

- 至少保留分析、知识、规划、执行四类角色
- 每个 Agent 的输入、输出、职责边界清晰

### 7. SSE 流式交互

- 前端支持流式输出
- 至少支持停止、重试、状态反馈

### 8. 基础可观测性

- 能看到 analysis / retrieval / plan / tool / answer
- 可以用于 bad case 排查

### 9. 最小评测样例

- 至少 40 条测试样例
- 覆盖订单、退款、登录、发票、地址修改、升级、越界请求、安全场景

### 10. GitHub 可发布材料

- README
- 架构说明
- 运行说明
- 配置说明
- 评测说明
- 已知问题与后续规划

## V1 明确不做的内容

以下内容不纳入 V1 范围：

- 生产级订单 / 工单系统深度集成
- 长期记忆系统
- 复杂权限和多租户机制
- 通用型万能 Agent
- 全量 MCP 生态接入
- 大而全场景覆盖

## V1 收官标准

### 功能收官标准

- 前后端可稳定启动
- 真实模型模式可运行
- `/ingest`、`/chat`、前端页面可用
- 至少两条工具链路正常
- 至少一条多轮会话可演示

### 工程收官标准

- 配置清晰，密钥不入库
- 目录结构清楚
- README 足够完整
- 没有明显 demo 拼装痕迹

### 质量收官标准

- 有最小评测集
- 能举出 3 到 5 个 bad case
- 能解释系统边界
- 回答质量整体稳定，没有高频明显幻觉

### 项目说明标准

- 能在较短时间内讲清项目
- 能解释为什么要用 RAG / Tool / Planner / Multi-Agent
- 能说明失败时如何定位问题
- 能说明设计权衡与后续演进路线

## V1 最终交付物

V1 结束时，仓库里至少应包含：

- 可运行代码
- `.env.example`
- `.gitignore`
- GitHub README
- 一套评测数据
- Trace Schema 和错误分类文档
- 一份 RAG 升级路线说明
