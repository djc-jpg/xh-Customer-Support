# RAG 升级路线

## 当前现状

当前项目已经具备最小 RAG 闭环：

- FAQ 文档导入
- 文本切分
- Embedding + Chroma 检索
- 无 key 时 TF-IDF fallback
- 检索结果参与回答生成

这已经能支撑当前版本的展示和验证，但在检索质量上仍有提升空间。

## 升级目标

RAG 的升级目标不是堆技术名词，而是回答三个问题：

- 为什么当前检索还不够好？
- 如何减少误召回和漏召回？
- 如何让最终回答更 grounded？

## 第一阶段：补齐评测

目标：先证明当前 RAG 哪些地方做得不够好。

建议动作：

- 对 40 条评测样例打标签，标记期望 FAQ topic
- 统计 `Hit@3`
- 记录误召回和漏召回 bad case
- 分析哪些 query 类型最容易失败

产出：

- RAG 评测结果表
- Top bad case 列表

## 第二阶段：优化检索输入

目标：让检索 query 更适合召回知识。

建议动作：

- 引入 query rewrite
- 对多轮问题做上下文改写
- 对混合问题做 query decomposition
- 区分工具问题和 FAQ 问题的检索策略

示例：

- 原始问题：`那它大概什么时候能到？`
- 改写后：`订单 O1001 预计送达时间如何查询`

## 第三阶段：升级召回策略

目标：减少只靠单一路向量检索带来的偏差。

建议动作：

- 从单一路向量检索升级为 Hybrid Retrieval
- 组合向量检索与关键词检索
- 为 FAQ 元数据加入 `topic / source / updated_at / priority`

设计上的考虑：

> 单一路向量召回对订单号、中文短问句、边界问法的鲁棒性不够，因此需要 Hybrid Retrieval。

## 第四阶段：增加重排

目标：先粗召回，再把最相关的结果排到前面。

建议动作：

- 在 top_k 粗召回后增加 rerank
- 如果没有单独 reranker，可先用轻量规则重排
- 优先保留与意图强相关的 FAQ

简单规则重排可以优先考虑：

- topic 标题匹配
- 问句关键词匹配
- 是否包含订单号 / 时间 / 发票等关键信息

## 第五阶段：增强 grounded answer

目标：回答要建立在证据之上，而不是把检索文本大段拼进去。

建议动作：

- 区分知识库事实与工具实时结果
- 工具结果优先于知识库泛化描述
- 回答中只保留最相关 FAQ 结论
- 知识不足时明确说“需要进一步确认”

重点优化方向：

- 不把整段 FAQ 原文直接拼到最终回答里
- 不让低相关命中污染最终回答

## 第六阶段：工程化增强

目标：让 RAG 成为可调优、可追踪的模块。

建议动作：

- 记录每次检索 query 与 top_k 命中
- 保存 RAG bad case
- 对不同 chunk 策略做对比
- 对不同 embedding 模型做对比

## V1 推荐做到的程度

V1 不必一次做完全部升级，建议优先做到：

- 有 RAG 评测
- 有 query rewrite 思路
- 有 metadata 优化
- 有简单 hybrid / rerank 策略
- 最终回答做到 grounded

## V2 再考虑的内容

以下内容可以留到下一阶段：

- 领域知识图谱
- 多知识库路由
- 长文档层级检索
- 专门 reranker 模型
- 复杂 query planning
